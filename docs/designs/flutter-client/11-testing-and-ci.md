# 11. Testing and CI

Status: design phase.

`AGENTS.md` rules apply to the client: test first for executable changes, assert on behaviour, no source-text tests, evidence with the `verify:` prefix.

Coverage: `flutter test --coverage` merged with the API package's; floor 80 % lines for `lib/core/**` and `packages/soundspan_api/lib/**`, 60 % overall, excluding `*.g.dart`, `*.freezed.dart`, and `generated/` directories. `tool/coverage_floor.dart` checks the floors in `tool/coverage_floor.json`. `tool/coverage_exclusions.txt` lists plugin-bound adapters that `flutter test` cannot run, one glob per line with a ` # reason`; an entry without a reason or one that matches no file fails the check. Drift table definitions (`lib/core/storage/<db>/tables/*.dart`) are read by `drift_dev` and never run, so they start with `// coverage:ignore-file`, which `flutter test --coverage` honours; the generated code they produce is excluded as `*.g.dart`. The floor is a ratchet: it is raised when exceeded by 5 points, never lowered. The check is advisory about the ratchet: it prints the new floor to commit and does not fail for it.

## Golden Tests

- Matrix per component or screen: widths 390, 800, 1440 × themes dark, light. Selected ones also at text scale 2.0, pseudo-locale, and RTL.
- Rendered with real fonts: `test/flutter_test_config.dart` loads the bundled Montserrat, Turret Road, and the Material icon font before any test and runs every test under the soundspan `AlchemistConfig`. One set of goldens exists, rendered on Linux with the Flutter version pinned in `.fvmrc` and stored beside each test under `goldens/`. Alchemist's obscured-text "CI" variant is off and no second image set is committed. On a host other than Linux, golden tests still build and pump, but the comparison is skipped and nothing is written.
- `test/helpers/golden.dart` provides `goldenMatrix(name, builder:, sizes:, themes:, highContrast:, textScales:, locales:, overrides:, act:)`: one test tagged `golden` per combination, pumped with `pumpApp` and the provider `overrides`, each image the whole surface (with `act`, which runs on the settled tree to open a menu or sheet, the whole app including the routes it opened), named `<name>.<width>.<theme>[.x<scale>][.<locale>].png` (the theme is `dark` or `light`, with `-hc` for high contrast; the scale is left out at 1.0 and the locale at `en`). Defaults: the three window-class sizes, dark and light.
- Updating: `tool/goldens.sh` runs `flutter test --tags golden --update-goldens` (extra arguments go to `flutter test`). On a Linux host with the pinned Flutter it runs directly; elsewhere it runs the same command in a container with that Flutter version through Docker or Podman, and fails with a clear message when neither is installed. When the `client-golden` job disagrees with committed images, commit the images from that run's `client-golden-rendered` artifact.
- Network images are replaced by a deterministic placeholder provider: `PlaceholderImageProvider(ref)` in `test/helpers/` resolves synchronously to a flat image whose colour is one of eight, picked by the sum of the ref's code units modulo 8.
- `test/helpers/guidelines.dart` provides `expectMeetsGuidelines(tester, contrastSamplingExempt:)`, which checks the tap-target size, tap-target label, and text contrast guidelines on the pumped tree.
- The text contrast guideline does not read a text colour: it takes the pixels inside the text's semantics node, splits them at their average lightness, and compares the most frequent pixel of each half. Short lines of thin glyphs at a device pixel ratio of 1.0 can defeat it: the player bar's artist line (`bodySmall`, 13 px at weight 400, in `contentSecondary` `#525252` on `surfaceRaised` `#FAFAFA`) renders `#525252` pixels, yet in light no single shade of its anti-aliased edges outnumbers the others, so the sampler reports an edge grey (`#D3D3D3`, 1.43:1) as the text colour. The rendered colour is a pair the token table allows at 4.5:1 and the token contrast test proves it; the guideline threshold is not lowered and the typography is not changed to suit the sampler. Instead `contrastSamplingExempt` takes finders whose semantics nodes, and only those, the contrast check skips. Each use is limited to the theme where the sampler fails and sits next to an assertion that the text's style colour is the expected token. Uses: the player bar's artist line in light (`player_bar_test.dart`, `right_panel_test.dart`).

## Contract Suite

Shapes are proven on the server: P9 validates every client-surface response against its schema ([12](12-server-prerequisites-p6-p9.md)). The contract suite proves what a schema cannot: sequences, headers, status codes, and that the generated client and the hand-written transport work against a real server together.

**Server under test.** `client/contract_test/compose.yaml` runs three services that `extends` the repository's `docker-compose.yml`: `backend`, built from the working tree's `backend/` (with the `media-metadata-contract` additional context), so it is the pull request's own backend; `postgres` (pgvector); and `redis`. A fourth service, `podcast-feed` (`nginx:1.27-alpine`), serves the fixture podcast read-only from `./.fixtures/podcast` at `http://podcast-feed/feed.xml`; the backend starts after it is healthy. The backend refuses feed and enclosure hosts that resolve to private, loopback or link-local addresses (`backend/src/services/outboundUrlSafety.ts`), so the compose network uses the subnet `11.86.0.0/24`, outside every range it blocks; the server's rules are not relaxed. Differences from the root file: `OPENAPI_VALIDATE_RESPONSES=1`, so a response that does not match its schema answers 500 with `code: RESPONSE_SCHEMA_MISMATCH` and fails the test that caused it; `BACKEND_PROCESS_ROLE=all`; `AUDIO_ANALYSIS_ENABLED=false`; no sidecar, analyzer, frontend or worker services; `./.fixtures/music` mounted at `/music`; named volumes only; the backend published on `127.0.0.1:13006` and PostgreSQL and Redis not published; the root health check. The variables the root file marks required (`POSTGRES_PASSWORD`, `SESSION_SECRET`, `SETTINGS_ENCRYPTION_KEY`, `INTERNAL_API_SECRET`) come from the committed `client/contract_test/.env`, fixed throwaway values that Compose reads for both files. Optional providers (TIDAL, YouTube) are not configured. Remote-source behaviour is covered on the server side by the Unified Playback Smoke job; the client suite asserts only that a disabled source yields `SOURCE_UNAVAILABLE` in the expected shape.

**Package.** `client/contract_test` is a pure-Dart package (`soundspan_contract_test`) with a path dependency on `soundspan_api`, its own lockfile and `analysis_options.yaml` including the client's. `dart_test.yaml` declares the tags `contract` (needs the seeded server) and `contract-destructive` (needs the server and changes its state for later tests). Tests without either tag need no server and run in `client-test`. `test/support.dart` loads the credentials, builds an anonymous or signed-in `SoundspanApi` (password login, then an in-memory `CredentialProvider`), and wraps every adapter in a guard that fails the test, naming the request, when any JSON response carries `code: RESPONSE_SCHEMA_MISMATCH`.

**Fixture library.** Generated, not committed. `fixtures/generate.sh` writes one tagged FLAC sine tone per track listed in `fixtures/library.json` (artist, album, year, disc, track number, title, frequency, length) under the git-ignored `.fixtures/music/<artist>/<album>/`, with `ffmpeg` and `jq`, each with the same embedded 600 × 600 PNG front cover, which the scanner extracts as the album's cover art: 3 artists, 6 albums, 40 tracks of 3 seconds, one album on two discs, one track of 30 seconds for Range cases, and one track with a Vorbis `LYRICS` comment holding LRC text. The scanner does not read lyrics; the lyrics service reads that tag from the file through `music-metadata` (`common.lyrics`) when lyrics are requested and no LRCLIB result exists. Output depends only on `library.json` and the `ffmpeg` build (bit-exact flags, fixed frequencies), and tests read `library.json` for expected counts and titles. The same script copies `fixtures/podcast/feed.xml` (the RSS feed "Contract Cast": two episodes, "Second Signal" of 8 seconds and "First Signal" of 6 seconds, newest first) to the git-ignored `.fixtures/podcast/` and writes the two MP3 sine tones its enclosures name beside it.

**Seed.** `node client/contract_test/seed.ts` (Node 24 type stripping; `fetch` and `node:crypto` only, no dependencies, no database access) asserts every response and exits 1 on the first failure:

1. waits until `GET /api/health` reports `startupComplete` (3 minutes);
2. `GET /api/onboarding/status` reports `needsOnboarding: true`;
3. registers `admin` through `POST /api/onboarding/register` (the first account is the admin) and completes onboarding;
4. creates `listener` and `twofa` (role `user`) through `POST /api/auth/create-user`;
5. enables 2FA for `twofa` (`/2fa/setup`, an RFC 6238 code computed from the returned secret, `/2fa/enable`) and checks that its password login answers `requires2FA`;
6. starts a scan and polls it to `completed` (5 minutes), then checks the artist, album and track totals against `library.json`;
7. creates a playlist of `listener` and adds the first five tracks by `playbackId`;
8. likes three further tracks of `listener` (`POST /api/library/preferences`, `thumbs_up`) and records one 30-second play of the first playlist track (`POST /api/plays`), then checks the liked total and that `GET /api/library/recently-listened` is not empty;
9. requests `GET /api/playback/stream/td.1` as `listener`: the contract server has no TIDAL streaming, so it answers `409 SOURCE_UNAVAILABLE` without any provider. The seed is server-side fixture code and may compose this id; client code and tests treat it as opaque. Any other answer records `null` with a warning, and cases that need the id skip;
10. subscribes `listener` to `http://podcast-feed/feed.xml` (`POST /api/podcasts/subscribe`) and checks that the podcast's detail lists at least two episodes;
11. writes the git-ignored `.seed/credentials.json`: `baseUrl`, `admin`, `listener` and `twofa` with passwords, `totpSecret`, `playlistId`, `unavailablePlaybackId` (string or null).

Not seeded: a device-link code (added with the device-link group).

**Running it.** `client/contract_test/run.sh` is the local equivalent of the `client-contract` job: `fixtures/generate.sh`, `docker compose -f compose.yaml up -d --build --wait`, `node seed.ts`, `dart test --tags contract`, `dart test --tags contract-destructive` (an empty selection, exit code 79, passes), and always `docker compose -f compose.yaml down -v`. It needs Docker with Compose, `ffmpeg`, `jq`, Node 24 and the Dart SDK of the pinned Flutter release, and leaves `git status` clean.

**Destructive tests run last.** A test that leaves the server unusable for the tests after it carries the tag `contract-destructive` instead of `contract`, lives in its own file, and runs in the second `dart test` step, after every `contract` test and as the last step before the server is torn down; nothing is added after that step. The login rate limit is the case: `test/rate_limit_test.dart` sends failed logins (at most 45) until the server's login limiter answers 429, which blocks every login from the runner's address, correct ones included, for the rest of its 15-minute window. Within the `contract` tag tests do not depend on each other's order: each signs in for itself. TOTP codes for the `twofa` account are computed in the test from `totpSecret` (`test/support/totp.dart`: RFC 6238, HMAC-SHA1, 30-second step), and `InMemoryCredentialProvider` records every `onTokensRotated` and `onUnauthenticated` call so tests can assert how often the transport refreshed or ended a session.

**Tests.** One group per table in the endpoint inventory ([03](03-api-layer.md)). Each calls every operation in its table through the generated client at least once, which exercises decoding and the server's response validation in one step. Behavioural cases:

- Login, refresh rotation, refresh with a rotated-out token, 2FA challenge shape, rate-limit body is plain text with `Retry-After`.
- Library and browse: artist offset paging with `total`, no overlap between pages and a returned `nextCursor` accepted; albums filtered by `artistId`; disc and track numbers on the two-disc album; liked keyset paging across two pages ending with `hasMore` false; playlist items in seeded order with `playback.isPlayable`; search by track, album and artist name; catalogue search decoding with optional providers off; cover art at the snapped size with a credential and 401 without; mixes decoding or `FeatureDisabled`; top podcasts decoding or `Upstream`/`ServerError`.
- Device-link verify with a code generated through the seeded web session; API key works on JSON, stream, image, and socket; `?token=` with an API key is rejected.
- `GET /playback/stream`: `200`, `206` with `Range`, strong `ETag`, `If-Range` match and mismatch, `quality` variants, each error code.
- P6–P8 behaviours ([12](12-server-prerequisites-p6-p9.md)), including a play reported with `playedAt` and `listenedMs`, its idempotent retry, and a play under 5 seconds not being recorded.
- Offline: request album and playlist, complete, list, revoke through the admin switch, delete, cache-limit error body.
- Playback state round trip with `X-Playback-Device-Id`; queue truncation at 100.
- Playlist add, remove, and reorder by `playbackId`.
- Podcasts: the seeded podcast in the subscribed list and its detail with episode durations; the episode stream through `StreamUrls.episode` with `200` and `206` for `Range`; progress posted and then finished shows on the episode; unsubscribe removes it and subscribing with the feed URL restores it; an unauthenticated list is 401. The directory's top list reaches an external directory and stays in the library and browse group.
- Socket handshake with JWT and with API key; queue add by `playbackId`.
- Feature-disabled 404 shape.

**Fixtures.** `client/contract_test/tool/capture_fixtures.dart` lives in the contract package because it uses that package's server support code and must not import Flutter. It runs against the same seeded server (`.seed/credentials.json`) and holds a declared list of capture steps, one per operation with a JSON 2xx response and one per response shape where an operation has several (`login.json`, `login.requires2FA.json`). Each step sends its request through a Dio built by `createDio` (base-URL guard and credential interceptors) that returns the raw body; the tool scrubs it (values under `token`, `refreshToken`, `apiKey`, `secret`, `password` and `passwordHash` become `<redacted>`, `email` becomes `user@example.invalid`, at any depth), and writes `<operationId>[.<variant>].json`, pretty-printed with sorted keys, to `--out` (default `packages/soundspan_api/test/fixtures/`). Binary and empty-body operations are not captured. The `client-contract` job runs it after the `contract` tests and before the destructive ones and always uploads the result as the `client-captured-fixtures` artifact; `run.sh --capture` does the same locally. To create or refresh fixtures, download that artifact from the pull request's run and commit its files. Ids, names and timestamps are kept as the server sent them, so fixtures are not checked for freshness: they are regenerated when the spec changes. The client issue that first uses a group of operations adds their capture steps, fixtures and `decode_smoke_test.dart` table entries; that test checks that every fixture has a table entry and every entry a fixture, not that every operation of the spec is captured.

**Version matrix.** Nightly, `client-nightly.yml` runs the suite through `client-contract.yml` against a matrix of server refs: the client's own commit is the client, and the backend is built from the matrix ref. The matrix is `main`; `minServer` and the latest release join it once a server release exists. A failure on `main` is the early warning that a server change breaks the client.

## CI Workflows

### `client-quality.yml`

```yaml
on:
  pull_request:
    paths:
      - "client/**"
      - "backend/src/routes/**"
      - "backend/src/openapi/**"
      - ".github/workflows/client-*.yml"
      - ".github/actions/client-flutter/**"
      - "CHANGELOG.md"
  push:
    branches: [main]
    paths: ["client/**"]
```

Server-only PRs do not trigger it, except route and `backend/src/openapi/**` changes, which run the spec check and the contract job only, and `CHANGELOG.md` changes, which run the release dry run only.

A first job, `changes`, diffs the pull request against the merge base with its base branch using plain `git diff --name-only` and sets twelve outputs: `client` (`client/**`, the client workflows, or the composite action changed), `apple` (`client/ios/**`, `client/macos/**`, `client/pubspec.lock`, `client/lib/platform/**`, `client-quality.yml`, or the composite action), `api_surface` (`client/packages/soundspan_api/**`, `client/tool/specs/**`, `client/tool/spec_compat.dart`, `backend/src/routes/**`, `backend/src/openapi/**`, or `client-quality.yml`), `contract` (the `api_surface` paths plus `client/contract_test/**`), `web_storage` (`client/lib/platform/**`, `client/web/**`, `client/integration_test/web/**`, `client/pubspec.lock`, or `client-quality.yml`), `desktop` (`client/linux/**`, `client/windows/**`, `client/lib/platform/desktop_shell/**`, `client/lib/app/shell/window_state_controller.dart`, `client/integration_test/desktop/**`, `client/tool/ci/**`, or `client-quality.yml`), `device` (`client/lib/core/playback/engines/**`, `client/integration_test/**`, `client/lib/platform/player_engine/**`, `client/lib/core/playback/media_controls/**`, `client/lib/platform/media_controls/**`, `client/android/**`, `client/ios/**`, `client/windows/**`, `client/packages/soundspan_smtc/**`, or `client-device-tests.yml`), `device_suites` (the job groups of `client-device-tests.yml`: `engine` when `device` is true, `desktop` when `client/integration_test/desktop/**`, `client/lib/app/**`, `client/lib/platform/**`, `client/linux/**`, `client/windows/**`, `client/macos/**`, `client/pubspec.lock` or `client-device-tests.yml` changed, `all` when both, otherwise `none`), `workflows` (any `.github/workflows/client-*.yml`, `scripts/ci/client-nightly-report.mjs` or its test), `downloads` (`client/lib/platform/downloader/**`, `client/lib/core/downloads/**`, `client/integration_test/downloads/**`, `client/integration_test/support/throttled_file_server.dart`, or `client-quality.yml`), and `release_build` (`client-build.yml`, `client-release.yml`, `client/tool/release/**`, `client/pubspec.yaml`, `client/pubspec.lock`, `client/config/**`, or any of `client/android/**`, `client/ios/**`, `client/linux/**`, `client/macos/**`, `client/windows/**`, `client/web/**`), and `release_notes` (the `release_build` paths plus `CHANGELOG.md`). It also outputs `version`, the `version` of `client/pubspec.yaml` without its build number. On `push` every output is true and `device_suites` is `all`. Because the diff is against the base branch and not the previous push, a job that failed on an earlier push cannot be skipped on a later one. The analyze, test, golden, Android, Linux, web, and Windows jobs run when `client` is true; the Apple job runs when `apple` is true; the web integration job runs when `web_storage` is true; the desktop Linux job runs when `desktop` is true; the contract job runs when `contract` is true; `client-device-tests` runs when `device_suites` is not `none` and passes it as `suites`; `client-workflows` runs when `workflows` is true; `client-downloads-integration` runs when `downloads` is true; `client-build-dry-run` runs when `release_build` is true; `client-release-dry-run` runs when `release_notes` is true.

Every client job sets Flutter up with the composite action `.github/actions/client-flutter`: on Linux it installs the build packages of [01](01-toolchain-and-repository.md) (plugin native-asset hooks run during `flutter test` and need GTK and X11 headers), then it reads the version from `client/.fvmrc` with `jq`, installs it with `subosito/flutter-action`, caches Flutter on `.fvmrc` and pub on `.fvmrc` plus the `pubspec.lock` files of the client, the API package, the `soundspan_smtc` plugin and `contract_test`, and runs `flutter pub get` in `client/` and in `packages/soundspan_smtc`, and `dart pub get` in the API package and in `contract_test`.

macOS minutes are the expensive ones, so on pull requests the Apple job runs only when the diff against the base branch touches `client/ios/**`, `client/macos/**`, `client/pubspec.lock`, `client/lib/platform/**`, `client-quality.yml`, or the composite action, and always on a push to `main`. Whenever it runs it is blocking, so a pull request cannot leave the Apple builds broken.

**macOS switch.** Hosted macOS runners can queue for a long time, so every job on a macOS runner in `client-quality.yml` runs only when the repository variable `CLIENT_MACOS_CI` is `true` (`gh variable set CLIENT_MACOS_CI --body true`): `client-build-macos-ios`, `engine-conformance-ios`, `engine-conformance-macos` and `desktop-integration-macos`, and `build-macos` in the dry run (`client-quality.yml` passes `macos: ${{ vars.CLIENT_MACOS_CI == 'true' }}` to `client-build.yml`). With the variable unset these jobs are skipped, and a skipped job does not fail the pull request. The tag-triggered release always builds macOS.

Actions are pinned by commit SHA, as in the existing workflows. Flutter and pub caches are keyed on `.fvmrc` and `pubspec.lock`. Every Android job caches Gradle through `actions/setup-java` (`cache: gradle`, keyed on the Gradle files under `client/android/`).

### `client-build.yml`

### `client-device-tests.yml`

Reusable (`workflow_call` only), `permissions: contents: read`, actions pinned by commit SHA, Flutter from `client/.fvmrc` through the composite action. Its input `suites` (`engine`, `desktop` or `all`, default `all`) selects the job groups: the `engine-conformance-*` jobs and the `desktop-integration-*` jobs.

**Engine suite.** Each `engine-conformance-*` job runs `integration_test/engine_conformance_test.dart` against the platform's real `PlayerEngine`, built by `createPlayerEngine()`. Natively the test starts the tone server (`integration_test/support/tone_server.dart`, a `shelf` server of WAV tones generated in Dart, with Range support, dedicated 404 and 401 paths, a throttled 60 s tone and the headers recorded per path) inside the app on the loopback interface and writes the local-file tone to the app's temporary directory. The gap tolerance is 20 ms on the Android emulator, Linux and Windows, and 100 ms on the iOS simulator, whose index and position reports jitter around a transition (the `engine-conformance-ios` job passes `--dart-define=CONFORMANCE_GAP_TOLERANCE_MS=100`, because the app on a simulator cannot tell from its environment that it is not on hardware), and on macOS, whose transition is not reliably gapless ([06](06-playback.md)). Every job runs the engine with its production configuration, except the Windows job's null audio output, and is blocking. The iOS and macOS jobs run only when `CLIENT_MACOS_CI` is `true` (see **macOS switch**).

After the conformance run, every job runs `integration_test/media_controls_smoke_test.dart` as a further step against the platform's `MediaControls` from `createMediaControls()`: on the emulator as a second command of the same emulator script, on the simulator, macOS and Windows with `flutter test … -d <device>`, on the web with `flutter drive` through the same `chromedriver`, and on Linux under `dbus-run-session -- xvfb-run -a` (the job also installs `dbus`), so MPRIS registers on a session bus of the step's own, which the test lists. The playing state carries a thumbnail file the test writes to the temporary directory (none on the web). On Windows the controls are `SmtcControls`, which send without waiting, so a second case, skipped elsewhere, awaits every call of the `soundspan_smtc` plugin in turn through `WindowsSmtcGateway`.

### `client-release.yml`

Trigger: a pushed tag `client-v*`. `permissions: contents: read` at the top, one concurrency group per tag that is never cancelled, actions pinned by commit SHA.

| Job | Does |
|---|---|
| `validate` | Checkout with full history; `dart run tool/release/validate_tag.dart --tag <ref name> --pubspec pubspec.yaml`; outputs `version` |
| `build` | Calls `client-build.yml` with that version and the workflow run number as the build number; it builds with `--dart-define-from-file=config/release.json` and writes `SHA256SUMS`. Its artifacts are marked `-unsigned`; signing steps are added when signing is set up |
| `draft-release` | Fails without changing anything when a release for the tag exists. Finds the previous tag (`git describe --tags --abbrev=0 --match 'client-v*' <tag>^`) and takes its `CHANGELOG.md` with `git show`; `tool/release/release_notes.dart` writes the notes; downloads `client-release-files`, checks `SHA256SUMS`, creates build-provenance attestations for every file, and runs `gh release create <tag> --draft --prerelease --title "soundspan client <version>"` with the notes and every file. Only this job has `contents: write`, `id-token: write` and `attestations: write` |
| `publish` | Runs in the `client-release` environment, whose required reviewers are the manual approval; `gh release edit <tag> --draft=false --prerelease` publishes the draft as a **pre-release** |

`validate_tag.dart` accepts `client-v<version>` where `<version>` is `MAJOR.MINOR.PATCH` with an optional pre-release (`-rc.1`) and no build metadata, equal to the `pubspec.yaml` `version` without its `+build` suffix; it prints the version, or both values and exit code 1.

`release_notes.dart` collects every bullet under every `### Client` subsection of the changelog, in order, leaves out the bullets that appear word for word in the previous tag's changelog (with no previous tag, every bullet is included), and writes fixed English text: a paragraph saying these are unsigned test builds (Windows SmartScreen and macOS ask for confirmation, the debug-signed Android build must be uninstalled before a later signed build installs, there is no iOS build), "Works with soundspan server `<minServer>` to `<maxTestedServer>`" from `BuildConfig`, a "Changes" list or "No user-visible client changes.", and a "Verify downloads" line naming `SHA256SUMS` and `gh attestation verify`.

A tag trigger cannot run from a pull request, so `client-release-dry-run` in `client-quality.yml` runs both scripts and `actionlint` instead. Pushing the web image to GHCR as `ghcr.io/<repo>-client-web:<version>`, installers and packages, and desktop appcasts (M5) are not part of this workflow yet.

### Local Equivalents

`client/tool/verify.sh` runs the `client-analyze` and `client-test` jobs. The root `package.json` gains `verify:client` (calls it) and it is listed in `AGENTS.md`'s verification table. `npm run verify` does not include it; client work runs `verify:client`, server work is unchanged.

## Gates Specific to the Client

| Gate | Tool | Fails when |
|---|---|---|
| Generated code is current | `tool/gen.sh` + diff | Any generated file differs |
| Layering and platform imports | `tool/check_imports.dart` | A rule in [01](01-toolchain-and-repository.md) is broken |
| Source-agnostic client | `tool/check_imports.dart` | Banned identifiers appear under `client/lib` or the API package |
| No hard-coded UI strings | `tool/check_l10n.dart` | A literal reaches a text widget |
| Platform configuration | `tool/check_platform_config.dart` | An entry the app needs is missing from the Android manifest, the iOS or macOS `Info.plist`, or the Linux `.desktop` file (the `soundspan` URL scheme: intent filter, `CFBundleURLTypes`, `Exec=… %u` and `MimeType=x-scheme-handler/soundspan;`, `Icon` and `StartupWMClass`), or a camera entry of the QR scanner from the Android manifest, either `Info.plist` or the macOS `.entitlements` files; the iOS and macOS `Info.plist` rows, the macOS entitlements and the iOS privacy manifest of doc 10 (a missing or wrong key, a background mode other than `audio`, `NSAllowsArbitraryLoads`, a missing entitlement, tracking true, a required-reason category or reason other than the listed ones); prints every missing or unexpected entry with its file. `client-build-macos-ios` runs it on the built bundles too |
| Token contrast | Unit test | A text/surface pair is under its ratio |
| Spec is current and compatible | `client-spec` job | The committed spec differs from the backend's, or breaks compatibility with the `minServer` snapshot (`tool/specs/min-server.json`; kinds `operation-removed`, `response-field-required`, `response-type-changed`) |
| Dependency licences | `tool/license_audit.dart` | A dependency's licence is not on the allowlist (MIT, BSD-2/3, Apache-2.0, MPL-2.0, ISC, Zlib, LGPL for dynamically linked native libraries); GPL-only fails. The audited set is the transitive closure of the non-dev dependencies of the app and of `soundspan_api`, without Flutter SDK packages. LGPL needs a `linking: dynamic` entry in `tool/license_overrides.yaml`; an unrecognised or missing licence text needs an entry naming an allowed licence; an entry for a package outside the audited set fails. Also fails when a font file (`.ttf`, `.otf`, `.ttc`, `.woff`, `.woff2`) under `assets/fonts/` has no non-empty licence text at `assets/licenses/fonts/<Family>.txt`, where the family is the file name up to its first `-`; when a file under `assets/licenses/` is not named by an entry of the notice manifest `assets/licenses/index.json` (`title`, `file`, `spdx`, `platforms`), an entry names a missing file, or the manifest is missing or malformed; and when `pubspec.lock` contains a `media_kit_libs_*` package while `assets/licenses/mpv-NOTICE.txt` or `FFmpeg-NOTICE.txt` is absent |

## Signing and Store Distribution

Deferred until the software is ready for v1, and not tracked as tasks. Until then `client-release.yml` produces unsigned pre-release artifacts: a debug-signed APK, Windows `.exe` and MSIX, an ad-hoc signed macOS `.dmg` (opens after the user approves it in System Settings), Linux packages, and the web bundle. There is no iOS artifact, because iOS builds cannot be distributed without an Apple account; iOS is exercised in the simulator and on developers' own devices. Release notes state that the artifacts are unsigned test builds.

One consequence to plan for when signing starts: Android installs an update only over a build signed with the same key. Testers will have to uninstall a debug-signed pre-release once before installing the first properly signed build, which removes its local data. The remaining signing and store work is listed in [13](13-milestones-and-work-breakdown.md).

## Manual Release Matrix

A checklist issue template, modelled on `docs/NATIVE_AUDIO_ENGINE.md`'s validation pattern. Sections:

- **Playback:** gapless album on each platform by ear; seek; quality switch; loudness modes; podcast resume and speed.
- **Interruptions:** phone call, alarm, another media app, headphones unplugged, Bluetooth connect/disconnect, AirPods/headset buttons.
- **Background:** 1 hour screen-off playback on Android and iOS; app swiped away on Android; device reboot then play from notification.
- **OS controls:** lock screen and notification (Android), Control Center and lock screen (iOS), Now Playing and media keys (macOS), SMTC flyout and media keys (Windows), MPRIS in GNOME and KDE (Linux), Media Session in Chrome.
- **Cars:** Android Auto Desktop Head Unit: browse, play, voice search, offline.
- **Network:** Wi-Fi → mobile handoff mid-track; airplane mode mid-track with and without downloads; captive portal; server restart during playback; reverse proxy with sub-path; LAN `http://`.
- **Offline:** download album and playlist; kill app mid-download; resume; revoke from the server; quota reached.
- **Accounts:** password with 2FA; device link by code and by QR; expiring key; two profiles on one device.
- **Accessibility:** scripted pass with each screen reader; keyboard-only pass on desktop; text scale 2.0.
- **Resource budgets:** the table in the design document, measured with the platform profiler, recorded in the issue.
